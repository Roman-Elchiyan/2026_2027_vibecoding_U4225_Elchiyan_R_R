## 2. Поиск и источники

| Источник | Реализовано | Живой smoke test |
| --- | --- | --- |
| PLOS Water CSV | Исходные FTS5/RapidFuzz/E5, точный DOI | 434 записи сохранены |
| OpenAlex | Тематический запрос, точный DOI, авторы, дата, восстановление abstract, доступ | 3 материала, 3 DOI, 3 аннотации |
| Crossref | Библиографический поиск и DOI lookup, User-Agent и `mailto` | 3 материала, 3 DOI |
| DataCite | Поиск DOI данных и материалов, описания, права | 3 материала, 3 DOI, 3 описания |
| World Bank D&R | Аналитические документы через `/api/v3/wds` | 3 документа с описаниями |

World Bank использует API документов, а не индикаторов. В `MetadataHTTP` реализованы `httpx`, максимум три одновременных HTTP-запроса, ограничение частоты по источнику, таймаут, один короткий повтор на 429/5xx и SQLite-кеш ответов на час. Исключение одного адаптера превращается в предупреждение; остальные материалы остаются доступны.

Работают выбор источников, годы, точный тип из метаданных, категории scientific/analytical, язык оригинала RU/EN, доступ open/restricted/unknown/any, количество 5/10/20/50 и порядок по релевантности источника либо году. Неизвестные год/язык/доступ не считаются подходящими под ограничивающий фильтр. Доступ не выводится из названия сайта; Crossref без явных сведений остаётся unknown. Число результатов обозначает размер сохранённой подборки, а не размер всех баз.

DOI ищется строго: публикации с другим DOI отбрасываются. Для тематического запроса результаты источников чередуются, устраняются дубли, сохраняется снимок. Перелистывание по пять результатов, избранное и история продолжают работать. Дополнительное E5-ранжирование внешних кандидатов включается отдельно, использует существующий единственный worker и кеш векторов; при занятости/таймауте остаётся порядок API.

## 3. Перевод и E5

Argos Translate 1.11.0 использует установленные Windows-пары ru→en и en→ru. Новые языковые пары не скачивались. Русский запрос переводится для английского лексического/API-поиска, а локальная E5 получает оригинал. Название в карточке остаётся исходным; русский перевод включается отдельно, аннотация переводится по кнопке. Авторы, DOI и поля ссылок не передаются переводчику.

Перевод выполняется одним worker вне Telegram event loop; повторные переводы кешируются в SQLite. При таймауте новые задачи не накапливаются, пользователь получает оригинал и предупреждение. Установленный Stanza пытался обновлять недоступный `resources.json`; вместо изменения моделей используется локальное разделение предложений на экземпляре переводчика. Файлы установленных пакетов и языковые веса не менялись.

Фактически получено:

- `водоснабжение и качество питьевой воды` → `water supply and drinking water quality`;
- `Water quality and climate change` → `Качество воды и изменение климата`;
- PyTorch остался `2.6.0+cu124`, E5 выполнилась на GTX 960 / `cuda`.

В интеграционном живом поиске русский запрос вернул **20 материалов за 8,623 с**, по четыре от CSV, OpenAlex, Crossref, DataCite и World Bank, без предупреждений. Точный DOI из оригинального CSV вернул одну запись. Снимок и избранное прочитаны после повторного открытия SQLite. Это разовое измерение, не нагрузочный тест.

## 4. LiteLLM и бюджеты

Используются `ghcr.io/berriai/litellm-database:v1.105.1` и `postgres:17.6-alpine`. Реальный OpenAI-ключ получает только LiteLLM; бот отправляет запросы на локальный Proxy с персональным virtual key. Master key используется исключительно `LiteLLMAdmin` для управления. Секреты пользователю не выдаются.

В Proxy настроены `research-basic → openai/gpt-6-luna` и `research-complex → openai/gpt-6.1-sol`. В работающем контейнере проверены `/v1/responses`, `/model/info`, `/key/generate`, `/key/info`, `/user/new`, `/user/update`, `/key/update`, readiness и PostgreSQL. Пользовательские ключи разрешают только `research-basic`; Sol явно помечена недоступной до отдельной проверки разрешённого сценария. Автоматического перехода на Sol и web_search нет.

Начальный бюджет ключа — $0.50, без `budget_duration` и автоматического сброса. `/limits` читает фактические `max_budget` и `spend`; при недоступности Proxy остаток объявляется неизвестным. ИИ включается пользователем и конфигурацией, а бесплатный поиск работает независимо от него. Ограничены вход, выход и параллелизм; платные HTTP-запросы не повторяются автоматически. План повторного идентичного поиска кешируется, кнопка повтора результатов полностью пропускает ИИ. ИИ структурирует задачу и может отдельно объяснить релевантность уже найденной публикации; источники из памяти не добавляются в выдачу.

| Реальная проверка | Результат |
| --- | --- |
| Персональный virtual key и начальный лимит | Создан, $0.50, spend $0 |
| Ключ с заранее превышенным бюджетом | `/v1/responses` отклонён с HTTP 422 и сообщением о бюджете |
| Подтверждённое увеличение тестового лимита | $0.50 → $1.00 |
| Повторное подтверждение | Осталось $1.00, двойного начисления нет |
| Перезапуск обоих контейнеров | Ключ и лимит $1.00 сохранились, spend $0 |
| Первоначальный платный микрозапрос через Proxy | HTTP 401; отдельная диагностика OpenAI подтвердила `invalid_api_key` |
| Повторная проверка после замены ключа | **HTTP 200**, реальный ответ GPT-6 Luna; 13 входных и 5 выходных токенов |
| Стоимость и бюджет реального пользователя | $0.0000038 записаны в PostgreSQL; остаток $0.50 → $0.4999962 |

Для первоначального бюджетного smoke использовались отдельный служебный пользователь и изолированная SQLite. При повторной проверке владелец предоставил новый действующий ключ: `/v1/models` подтвердил доступность `gpt-6-luna` и `gpt-6.1-sol`. Генерация выполнена через настоящий `ResearchAI` и персональный LiteLLM virtual key владельца, без прямой платной генерации в обход Proxy. Стоимость ответа совпала с увеличением spend, уменьшением остатка и записью PostgreSQL. Ошибка 401 устранена заменой недействующего ключа; обычный пользовательский повтор после явного отказа разрешён, автоматического платного повтора нет.
