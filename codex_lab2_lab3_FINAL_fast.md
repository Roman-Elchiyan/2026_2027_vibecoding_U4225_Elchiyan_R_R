**Стек:** LiteLLM Proxy в отдельном контейнере + PostgreSQL с постоянным томом; зафиксировать проверенную версию/тег LiteLLM (не `latest`). В LiteLLM настроить только алиасы:

Luna использовать для структурирования запроса, выбора источников, нескольких вариантов ключевых фраз, краткого объяснения релевантности **только реально найденных материалов** и анализа обратной связи. LiteLLM Proxy должен иметь реально работающие **virtual keys + PostgreSQL** и учет расходов по пользователю. Не считать `Project spend limit` OpenAI жёстким ограничением: в API-проекте на скриншоте было `Limit not enforced`.

Функции LiteLLM virtual keys/budget нужно проверить в реальном контейнере и тестом превышения бюджета: успешный ответ API сам по себе недостаточен. Если web_search tool через LiteLLM действительно работает и его отдельная стоимость учитывается — можно подключить **опционально**, с ограничением вызовов и отдельным явным разрешением; иначе оставить выключенным. Не подменяй внешний поисковый API вымышленными ИИ-источниками. Если реальный API-ключ ещё не введён, тестируй адаптеры моками и покажи отдельно непроверенный живой этап.

Время непрерывной работы, повторную пользовательскую оценку и число участников описывай только если они реально известны; иначе оставь нейтральный пункт «дополнить после проверки».

## Lab 3 — локальный деплой Windows + ngrok, Docker Compose LiteLLM/PostgreSQL, безопасность и наблюдение

**Решение:** три *процесса/сервиса*, не три контейнера:
1. `bot.py` на Windows с имеющейся `.venv`, моделью E5 на GPU и локальным Argos; параметры из уже существующего `.env`.
2. `litellm` в Docker Compose на `127.0.0.1:4000`, доступ из Windows только локально. Master key не должен попадать в обычные LLM-запросы; использовать персональные LiteLLM virtual keys. Не публиковать LiteLLM UI/management API наружу.
3. `postgres` в Docker Compose только во внутренней сети, с persistent volume и корректными паролем, readiness/healthchecks. Данные SQLite и модели остаются в `runtime/` Windows, как в Lab 1.

**ngrok и Telegram webhook:** зарегистрировать бесплатный аккаунт ngrok, использовать назначенный dev-domain и локальный агент ngrok в Windows. Секреты из `.env`; не печатать их и не передавать в URL. В локальном боте добавить опциональный режим `BOT_RUN_MODE=webhook`: `Application.run_webhook(listen='127.0.0.1', port=8080, url_path=<WEBHOOK_PATH>, webhook_url=<NGROK_PUBLIC_URL>/<WEBHOOK_PATH>, secret_token=<WEBHOOK_SECRET_TOKEN>, allowed_updates=...)`, используя `python-telegram-bot[webhooks]`; HTTPS завершается на ngrok. Инициализировать webhook **только после запуска и проверки HTTPS-туннеля**, не путать `/getWebhookInfo` с `getUpdates`. Зарегистрировать секретный путь и проверять HTTP-заголовок `X-Telegram-Bot-Api-Secret-Token`; этот токен не равен BOT_TOKEN. Не публиковать административные маршруты HTTP, не подключать ngrok к порту LiteLLM. Обработать повторные доставки Telegram updates и ошибки соединения. Не подключать дополнительную HTTP-framework библиотеку без необходимости.

**Переходы:** по умолчанию сохранить `BOT_RUN_MODE=polling` для smoke-тестов без ngrok. Для webhook остановить polling, запустить ngrok через `ngrok http 8080` (при необходимости через authtoken в приватной конфигурации), получить фактический `https://...` URL из ngrok CLI / локального agent API, сохранить `NGROK_PUBLIC_URL`, после этого запустить `bot.py` в режиме webhook. Если free dev-domain уже назначен, использовать его без требования платного тарифа. Для возврата к polling корректно вызвать `deleteWebhook(drop_pending_updates=False)` и проверить статус, потом начинать polling. Не запускать одновременно 2 процесса с одним BOT_TOKEN. При перезапуске сохранить ключи и хранилища, контролировать доступность ngrok. Документировать, что webhook не обязателен для самого LiteLLM и не является контейнеризацией.

**Docker Compose:** конфигурация только `litellm` + `postgres`, pinned image versions, `restart: unless-stopped`, healthchecks, `depends_on` с readiness, именованный том PostgreSQL, закрытая сеть, только LiteLLM bound `127.0.0.1:4000`. `DATABASE_URL` со строкой Postgres задать только в контейнер LiteLLM и сконструировать безопасно из `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB`; не допускать утечки пароля в логах или Compose stdout. `.dockerignore` исключает `.env`, runtime, .venv, веса и логи. Команды PowerShell: `docker compose config --quiet`, `docker compose up -d`, `docker compose ps`, `docker compose logs -f --tail 100 litellm`, `docker compose logs -f --tail 100 postgres`, `docker compose restart`, `docker compose down` (**без `-v`**). Проверить локальный HTTP health LiteLLM, реальные virtual keys и spend/budget с безопасным микрозапросом. Проверить Windows `bot.py --check`, затем polling, затем webhook через ngrok. Если ngrok нельзя запустить, authtoken не указан или webhook не получает реальные Telegram updates: зафиксировать фактическую ошибку и результат диагностики, вызвать `deleteWebhook(drop_pending_updates=False)`, остановить ngrok, переключиться на `BOT_RUN_MODE=polling` (без ngrok), проверить реальное получение сообщений; не заявлять проверку webhook как успешную. Не оставлять два работающих экземпляра бота.

**Наблюдение и логи:** сохранить старую систему логирования Lab 1 (`runtime/logs/bot.log`, 5 MiB + 3 ротации). Добавить UTC-события: запуск/готовность, ошибки webhook, внешний API (источник, HTTP статус, длительность), поиск без текста, кеш, перевод (время/направление), LLM (модель, стоимость, статус), админские операции и отзывы. Отдельно `docker compose logs` и состояние PostgreSQL/LiteLLM; отдельно ngrok status/счётчики запросов. Секреты, пользовательские тексты и токены в логах не показывать. Для Lab 3 реальное время непрерывной работы и ресурсы измерять, не сочинять.


Логи бота уже реализованы в Lab 1 (`runtime/logs/bot.log`, 5 MiB + 3 ротации), не переписывай их без необходимости. Дополнить событиями: запуск/готовность, внешний API (название источника, статус, длительность), поиск (без пользовательского текста), кеш, перевод (длительность и направление), запрос LLM (модель, стоимость, исход), админские операции/фидбек. Secrets/tokens/DOI с персональными данными в логах не хранить; DOI открытых публикаций можно сохранять только при обоснованной необходимости. Предусмотреть JSON/text удобный для `docker compose logs`, UTC timestamps, ограниченное хранение. Показатели: число пользователей, запросов, ошибок, время ответов, использование памяти, расход LiteLLM; не выдумывать uptime без реального наблюдения.
