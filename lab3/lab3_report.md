## 1. Архитектура развёртывания

Бот запускается нативно на Windows через существующую `.venv`; Argos, E5, GTX 960 и локальные кеши сохранены. Docker Compose содержит **два** сервиса: LiteLLM и PostgreSQL. SQLite, языковые модели и Telegram-токен в контейнеры не копируются. LiteLLM слушает только `127.0.0.1:4000`, PostgreSQL не имеет опубликованного порта; его том `litellm_data` постоянный. Сеть БД — internal, отдельная сеть позволяет Proxy обращаться к провайдеру. У обоих сервисов есть healthcheck, restart policy и ограниченная ротация Docker-логов.

`scripts/prepare_services.py` создаёт стабильные локальные секреты в игнорируемом `runtime/`, не меняя `.env`. `postgres.env` содержит только параметры PostgreSQL, `litellm.env` — только master/salt, безопасно сформированный `DATABASE_URL` и OpenAI API key. В исходном пользовательском `env.lab23.template` обнаружились реальные ключи: они сохранены в приватном `runtime/recovered-template.env`, а шаблон обезличен. Значения в отчёт не включены. После попадания исходного шаблона в диагностический вывод ключи следует перевыпустить.

## 2. Polling и webhook

В `bot.py` поддерживаются polling и встроенный `Application.run_webhook()` PTB с `[webhooks]`. Перед webhook проверяется локальный ngrok API, HTTPS-адрес и целевой порт именно 8080. Webhook слушает loopback, использует отдельные случайные путь и `X-Telegram-Bot-Api-Secret-Token`. Заголовок проверяет настоящий HTTP-сервер PTB, административных HTTP-маршрутов нет. При потере туннеля монитор прекращает webhook и возвращает приложение в polling. Перед polling вызываются `deleteWebhook(drop_pending_updates=False)` и `getWebhookInfo`; запуск при оставшемся webhook запрещён.

Повторы update ID отсеиваются серверно в SQLite. Действия одного пользователя сериализуются; блокировка файла исключает два одновременно работающих экземпляра бота. В тесте попытка второго запуска была отклонена. Идентичный платный план кешируется, операции бюджета используют постоянный UUID и абсолютный целевой лимит.

| Проверка | Фактический результат |
| --- | --- |
| Telegram `getMe` | Подтверждён `@itmoftmi_err2026_bot` |
| Polling на Windows | Процесс дошёл до `bot_ready`, выполняет long polling |
| Удаление webhook | Telegram подтвердил пустой URL, обновления не сбрасывались |
| Установка и первый запуск ngrok | Получен `ERR_NGROK_4018`: на тот момент отсутствовал authtoken |
| Повторный запуск после предоставления токена | Токен безопасно передан через окружение; `ngrok diagnose` подтвердил таймаут CRL и `ERR_NGROK_8003/8008` |
| Попытка webhook при неподтверждённом туннеле | Записан `ngrok_unavailable`, автоматический возврат в polling |
| HTTP без заголовка / с неверным секретом | Реальный локальный PTB ответил 403 |
| HTTP с неверным путём | Реальный локальный PTB ответил 404 |
| HTTP с правильным путём и заголовком | 200, update попал в очередь PTB |
| Реальный входящий пользовательский update через ngrok | **Не проверен**: рабочего туннеля нет |
| Ручные действия пользователя после исправления ИИ | Владелец отправил `/limits` и `/admin`; обе реальные команды обработаны без ошибок, подтверждено журналом |

Токен владельца обнаружен в изменённом `env.lab23.template`, перенесён в приватный `.env`, шаблон очищен и исключён из Git. По заключительному решению владельца рабочий режим — polling; ngrok/webhook оставлены необязательными. Их сетевой сбой не является блокером принятого развёртывания. Внешний webhook не заявляется проверенным; TLS-проверки не отключались.

## 3. Администратор, бюджет и заявки

Каждая команда, callback и текстовый административный шаг проверяют `ADMIN_TELEGRAM_IDS` на сервере. Реализованы состояние сервисов, страницы пользователей, бан/разбан, разрешение ИИ, глобальная пауза новых поисков, управление локальной и внешней E5, заявки и отзывы. Избранное и управление лимитом доступны при паузе поиска.

Увеличение лимита на $0.50, $1.00 либо введённую сумму требует отдельного подтверждения с пользователем, старым лимитом, добавлением и новым лимитом. В SQLite фиксируются UUID, акторы, сумма, старое/новое значение, UTC-время, статус и связанная заявка. При неизвестном результате HTTP выполняется сверка фактического `max_budget`; повторное прибавление вслепую запрещено. Заявка пользователя содержит сумму и комментарий; администратор одобряет с подтверждением или отклоняет с ответом конкретному автору. Потраченные средства не сбрасываются.

В реальном LiteLLM проверены virtual keys, $0.50 исходного бюджета, увеличение тестового лимита до $1.00, повторное подтверждение без второго увеличения, отклонение превышенного бюджета и сохранение после перезапуска обоих контейнеров. Первоначальный 401 диагностирован как недействующий ключ OpenAI. После замены ключа запрос GPT-6 Luna через персональный ключ владельца завершился HTTP 200: стоимость $0.0000038, spend $0 → $0.0000038, остаток $0.50 → $0.4999962. Значение расхода отдельно прочитано из PostgreSQL. Блокировка `ENABLE_AI=false` устранена; ИИ включён для запуска и владельца, Sol не включается автоматически.

## 4. Отзывы и анализ

Пользователь оценивает всю выдачу либо конкретную публикацию от 1 до 5, добавляет комментарий и изменяет оценку. Хранятся user/search/material ID и история изменений. Чужие и истёкшие ссылки проверяются сервером. Отзывы остаются после очистки старых выдач, материалы избранного не удаляются.

Администратор видит страницы отзывов, детали, агрегированную оценку, статусы обработки, отвечает только автору выбранного отзыва. Для ИИ выбираются до десяти отзывов; передаются оценки и ограниченные комментарии без ID, с маскированием email, телефонов, ссылок, usernames и типичных сочетаний имён. Произвольный свободный текст нельзя считать гарантированно полностью обезличенным. Анализ использует отдельный virtual key и бюджет, не может менять код, доступ или лимиты. Механика и обезличивание проверены моками; живой анализ отзывов отдельно не запускался, поскольку повторную платную проверку ограничили одним коротким запросом GPT-6 Luna.

Рабочий режим бота при этом оставался polling, ngrok не запускался. Сырой протокол — `runtime/release-tests.txt`, публичный итог — [evidence/final_checks.md](evidence/final_checks.md).

Живой интеграционный поиск на русском дал 20 материалов от пяти источников за 8,623 с без предупреждений; E5 работала на CUDA, точный DOI дал одну запись, снимок/избранное прочитаны после повторного открытия БД. `pip check`, `bot.py --check --external`, `docker compose config --quiet` и healthcheck обоих контейнеров прошли. Проверена передача только необходимых env-переменных, отсутствие внешнего порта PostgreSQL и локальная привязка LiteLLM. Проверка известных секретов в отслеживаемых и новых исходных файлах не нашла совпадений.

При финальной подготовке Telegram `getMe` и `getWebhookInfo` подтвердили доступ к боту и пустой URL webhook. Удерживается блокировка единственного экземпляра; оба контейнера healthy. SQLite: `quick_check=ok`, ошибок внешних ключей нет; online backup проверена. Журнал существует и доступен для записи. Правила Git исключают секреты, runtime, SQLite, логи, резервные копии, модели и векторы; совпадений с известными секретами также не найдено в 185 доступных объектах истории Git. Старый единичный Telegram `TimedOut` остаётся в журнале как фактическое событие; текущая проверка связи прошла, приложение не перерабатывалось.

Сохранено логирование Lab 1: `runtime/logs/bot.log`, 5 MiB + три ротации, UTC. Добавлены события внешних API, кеша, перевода, поиска без текста запроса, LLM, бюджета, отзывов и переключения режима. Исключения выводятся без сообщения и исходных строк с секретами; HTTP-библиотеки не пишут URL Telegram. Для диагностики контейнеров предусмотрен `scripts/service_status.py` с маскированием локальных секретов.

Это короткое наблюдение, не доказательство длительного uptime или нагрузочной устойчивости. После него выполнялся контролируемый перезапуск для проверки fallback. Видео и длительное наблюдение: дополнить после проверки.

## 7. Что осталось неподтверждённым

Блокирующих ошибок для принятого polling не выявлено. Внешний поиск, ИИ, расходы и лимиты дополнительно подтверждены владельцем в Telegram; ниже перечислены границы проверки и необязательные дальнейшие действия.

1. Живой платный анализ отзывов отдельно не выполнялся: ограничились одним успешным коротким запросом GPT-6 Luna с фактическим расходом.
2. Внешний webhook и реальная доставка через ngrok: authtoken уже передаётся, но соединение блокируется таймаутом CRL/TLS (`ERR_NGROK_8003/8008`).
3. Повторная оценка улучшений пользователями, длительное наблюдение и видео. Реальные `/limits` и `/admin` владелец уже проверил.
4. Резервная Sol намеренно недоступна в интерфейсе до отдельной проверки разрешённого платного сценария; web_search не включён.
